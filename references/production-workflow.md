# 生产工作流细节（意图路由 / 变更传播 / 画布 / 执行契约）

> **何时读**：意图路由判为「续作 / 定向修改 / 阶段重做 / 活剧本修订」时；换模型/改时长/改画幅/改母版前；用画布生成端时；每批写 03/04/05 前（执行契约五条）。SKILL.md 只保留摘要与指针，本文件是这些规则的唯一家。

## 一、变更影响传播清单（V3.23——模型/时长/画幅/母版变更时先填，再动下游）

换模型、改时长、改画幅、改母版这类变更会同时影响六处；靠人记必漏（task2 版本链 V1→V3.3 每次都在六处手工同步）。**每次变更先更新 01「项目状态卡」，再填 01「变更影响传播清单」，用户确认后一次性改完，不留半同步。**

| 变更类型 | 必须同步的六处 | 先改哪 | 验收 |
| --- | --- | --- | --- |
| 换视频模型 | 01 目标模型/骨架/时长上限；02 目标模型/能力/参考图上限；03 画幅/参考图尺寸；04 语法层/段长/参考图语法；05 语音路线；06 剪辑/OSD；画布节点参数；check 口径 | 先 01+02，再 03/04，最后 06+画布 | check.py + A17；人工核对 04 每段参考图语法 |
| 改时长/分段 | 01 节拍表/时长预算/分镜表/情节点覆盖；03 情景图分级；04 段长/时间账/尾帧衔接；05 台词落点；06 时间轴/裁剪/转场；OSD 时间轴 | 先 01 节拍表与分镜，再 04/06 | K14 + A17 时间账；人工核对尾帧 |
| 改画幅 | 01 整体方案/分镜；02 构图锚；03 图片尺寸/构图；04 构图/安全区；06 裁剪/OSD；画布节点尺寸 | 先 01+02，再 03/04 | A19（画幅事实）+ 人工安全区 |
| 改母版/机位 | 02 母版事实清单；03 母版图与所有引用它的情景图；04 所有引用该母版的段；01 分镜机位列；06 OSD 安全区；画布母版节点 | 先 02 事实清单，再 03，再 04 | A19 + 母版验收门 |
| 改风格/色板 | 02 风格圣经/色板；03 全部提示词后缀；04 风格锁；06 调色；画布已生成图重跑 | 先 02，再 03/04 | A16/A17 风格锁逐字 |

执行纪律：

1. 变更前填表（写 01 变更记录），列出受影响文件/镜号/段号；用户确认后再动。
2. 一次性改完，不留半同步；每改一处跑对应门。
3. 变更完成后更新「项目状态卡」；状态卡是下一次变更的入口。
4. 画布/生成端改动按「生成端改动回写清单」与画布纪律回写。

## 二、活剧本修订：局部重排

> 实测教训：03 曾因此全量重写两次。

真实的 AI 视频制作不是一条直线：用户看到图之后会想加镜头、删一条线、改一段情节。GATE1.5 定稿锁的是**故事骨架与情节点清单**，不是分镜表——分镜表是活文档。

**局部重排四步**（只动受影响的部分）：
1. **改情节点清单**：增/删/改对应行，标注修订日期与依据（用户原话要点）——这是唯一需要动的"上游"
2. **判影响面**：新情节点触及哪些场景/角色/道具？→ 02 锚定表只在**新增实体**时补条目（已有锚定不动，改了才走失效传播）
3. **插镜号不重排**：用**稳定镜号**（下条）插入新镜头，已有镜号一律不变——已有 03/04 内容不失效
4. **只对新增/改动镜头写提示词**：追加进 03/04 对应节，标注修订日期；相邻镜头按"改一拍连读三拍"复查，其余不碰。**改动已有镜头的提示词时，台词/镜号/生成时长是冻结字段**——从 01 逐字搬运台词，写完逐字回读比对（硬规则 4）

**稳定镜号规则（硬门）**：镜号一经分配**永不重排**。插入用后缀式——S3 与 S4 之间加镜写 `S3a`（或在 01 分镜表加"S3a（v2 新增）"行），**不把 S4 改成 S5**。理由：重排会让 03 的资产引用矩阵、04 的段落、画布/生成端已建的节点全部错位，实测代价=03 全量重写。作废的镜头在分镜表标 `~~S3b~~（v3 作废）` 保留行号，不删行。

**段落制生产单元（V2.9——用户口述一段做一段的实际节奏）**：局部重排是**镜头级**的；当用户新增的是**一个完整剧情段**（口述一段新剧情→要情景图组→要视频节点→验收→再下一段），生产单元是"段"不是"镜"，按以下最小闭环走，**不重走 GATE1.5、不全量重排分镜表**：
1. **段入清单**：新段的情节点逐行追加进 01 情节点清单（标修订日期+用户口述要点），分配段号与稳定镜号（后缀式）
2. **判存量**：该段触及的场景/角色/道具先查 02 与 03 资产矩阵——已有锚定与参考图直接复用，只有**新增实体**才补锚定条目/出新资产图
3. **段内自包含生产**：该段的情景图组（按 L1-L4 分级）→ 视频段提示词（骨架 A）→ 台词（从 01 逐字搬运）——一套走完跑 `check.py --partial`，按下文四节完成文档机检与内容评审后续跑下一段；批次（全部段落）完成后统一汇报（量化结果+check 结果+未过项点名）。参考图未生成处写 `PLAN-<ID>` 挂图占位照常产出（见停点纪律 E2），不停下等图
4. **段验收后同步**：验收通过 → 01 分镜表补该段行、03/04 追加该段节、02 只在有新实体时动；尾帧描述写进该段记录（下一段的 SCENE CONTEXT 衔接锚）
> 与六阶段的关系：段落制**不是跳过阶段**，是把阶段2-6 按段切片执行——锚定（02）与剧本骨架（01 情节点清单）仍是全项目级的，段内只做该段的图片/视频/台词/剪辑条目。首批镜头仍守"先出第一段整套交用户验收再铺量"。

**修订记录**：每轮修订在 01 追加一条变更记录（改了什么/影响范围（镜号·情节点·阶段）/影响文件/用户原话要点），不重写历史节——01 的修订轨迹本身是中断恢复的依据。**单一写入点（V2.9）**：变更记录**只写在 01**；00/02 里不重复记变更历史——02 只改字段本身（锚定条目更新），00 只在集完成时更新剧情状态。三处都写=检索性差且必漏改一处。

**局部复审（不重走全项目 GATE）**：剧情、动作、台词、时长、镜头或生成提示词有实质改动时，按修订记录把改动的场、段和受影响的关联镜头标为「待复审」；未受影响范围保留原结论。按 `assets/templates-review.md` 复审当前稿及受影响的交接点，在 01 台账追加**版本或修订记录、范围、结论和证据**。旧稿 `PASS`、用户对旧稿的定稿或机检通过，都不覆盖这次改动。剧本改动未通过当前稿复审，不进入受影响的分镜与提示词；提示词改动未通过复审，不标记为正式交付。独立评审无法执行时标「待评审」，可请用户直接审当前稿并记录裁决，不把自检写成独立 `PASS`。

**生成端改动回写清单（V3.7）**：在画布/生成端改过提示词后，回写三处并逐字核对——①04 对应段落块 ②05 台词（如涉及）③01 分镜表（时长/衔接/修订记录）；OPEN 项关闭、PLAN/REF 绑定更新。手工双写容易漏，回写后跑 `check.py --partial`。

## 三、画布/生成端为源的项目（用户在工具里直接改）

用 Toonflow 类画布执行生成时，用户往往直接在画布上改提示词、挪节点、删节点——**此时画布是执行端的事实，01-06 是决策源**。两者关系：
- **不追求实时同步**（实测：靠喊"同步"才追上，且每次同步都是浪费）→ 改为**批量滞后同步**：一轮生成告一段落时集中同步一次，同步内容写"摘要卡"（节点 ID + 一行状态 + 与文档的差异点），不逐字回填全文
- **冲突裁决**：画布与文档不一致且用户已在画布上定稿 → **以画布为准**，文档记差异并更新决策（不是把画布改回文档）
- **定稿标记**：用户在画布上自创的"定稿图另存防污染"节点是有效实践 → 文档的资产矩阵登记定稿标记节点 ID，重生成时不覆盖
- **发送前回读（每个正式视频段）**：已有画布或生成端时，取实际将发送的完整提示词与参考绑定（占位符展开后），按 `assets/templates-review.md` 的 04 评分卡对照最新用户裁决、01/02 和 `04` 交付稿；纯文档交付则复核最终可复制提示词，不能声称已核验画布。记录节点 ID 或交付文件位置及证据。发现旧动作残留、内容冲突或绑定不一致，先修正并回读；拿不到最终文本或绑定时标「发送前待核验」。**当前稿局部复审、拟发送段的内容评审或发送前回读有任一未通过（含待审/待核验），不得报告「可生成」，即使节点已建。** 这是验收动作，不是调用生成 API 的授权。
- **节点 ID 只查表，不猜（V3.7）**：画布节点 ID 的唯一来源是项目对照表（02/03 资产矩阵、画布摘要卡）；agent 不得凭记忆或相似度推测编造 ID。表里没有 → 停下查表或问用户，**不连接/不操作未经登记的 ID**（实测：猜 ID 会连错节点或整批静默不执行）
- **外部写 JSON 三件套（V3.23 实测）**：①写前备份带时间戳的副本（`画布1_YYYYMMDD_HHMMSS.bak.json`）；②确认画布软件未打开或已暂停自动保存；③写完立刻验证文件时间戳/大小/哈希。**优先按 label 更新现有节点，不删除重建**（重建会换 ID）；发现被自动保存覆盖 → 停，恢复最近备份，不重复写同一内容。操作细节见 execution-pitfalls 第 7 节
- **ref 编号=连线创建顺序（V3.15 修正）**：**append 通常只新增编号（ref7/ref8）、不打乱既有序**——提示词只需在挂图顺序表追加；只有"中途插入导致既有 ref 重排"才删全部入线、按最终顺序重连。无论哪种，**04 挂图顺序表必须同步改**，并逐条核对 `{{ref N}}` 与用途声明一一对应（旧画布实测 v21/v22 插入错位）
- **生成端只能全文重发时的版本账（V3.9 实测；当前画布 setPrompt）**：生成端没有局部编辑，每次重发前先把当前 prompt 存成版本摘要（版本号+改动点）写进 01 变更记录；重发后与 04 文档对比，禁止凭上下文记忆当前版本（带错版本=整段返工）。**换画布软件后本纪律保留，具体操作按新工具重写。**
- **同步触发**：用户说"同步"、或一轮生成结束、或进入阶段5/6 之前——三个触发点，其余时间不同步

## 四、执行契约（V3.16——防"没按 skill 执行、遗漏、凭记忆"）

> 实测教训：规则写得再全，执行时没读到、没照着做，产出仍会参差。以下六条把"执行"变成可留痕、可机检的动作，不只靠自觉。

1. **写前重读（硬动作）**：每批写 03/04/05 前，重新打开 **02 全文 + 01 当前段分镜行 + 05 台词行**；在 01「批次校验记录」写依据（`02:行号 / 01:行号 / 05:行号`）。项目文件**不受"同一文件一次会话只读一遍"限制**——那条只约束 references。可用 `pack.py freeze` 生成冻结字段速查卡辅助复制（带源行号），但**不替代重读**。
2. **段生产卡（每段一行）**：从 01/02 复制填——生成时长｜镜号｜台词落点｜**台词朗读(s)/动作(s)/镜头(s)**｜道具状态｜服饰/配饰（帽/须）｜**在场/位置（每人场景锚点+坐/站/走）**｜入画人数｜参考图绑定｜声音模式｜单镜理由｜峰值归属。另填「段状态账」（帽/须/道具在不在/服装版本/**在场位置**/依据 02 行号）。**时间账 `朗读+动作 ≤ 镜头`；状态三问与走位必须与 02/段状态账一致。**
3. **批次校验留痕**：每批在 01 追加 A1-A16 逐项记录（`PASS / OPEN / NA + 证据文件:行或镜号`）+ **K17/check 结果行**；没有留痕 = 该批未完成。OPEN 必须写回填时点。**04 只保留段/镜头标题**——修正说明/变更记录一律写 01（A17 会报非段落标题）。
4. **批次验收必须通过 A17 + K17**：A17 检查段卡/段状态账/批次校验记录/**参考契约（锁定+不复刻）/时间账/风格锁逐字**/04 段锁定清单九项/**走位总谱+逐镜动线+背景动作线/动作桥/人物道具群像就地绑定/负面段闭环/每镜焦段/光影演变线**，不替代内容质量评审；K17 检查 04/03 正向正文的音乐类词、无台词声明和声音正向收尾（【负面提示词】节跳过）。
   - **默认门与验收分开**：A17 不在默认 K1-K17 中，`--batch milestone` 也不含 A17。Python 侧的 `--batch 04` 同时运行 A17 和 K17；如果两者尚未核验齐全，可另跑 `check.py <项目目录> --gate A17,K17`（中间批只核对已有文档时加 `--partial`）。这不替代阶段末的默认门校验。
   - **Node 降级不是完整验收**：`check.mjs` 委托 Python 时可以运行 A17；本地 K1-K17 子集不运行 A17。若跳过 A17，即使子集全过也要在 01 和批次汇报中标为「A17 未核验」，待 Python 补验前不得声称本批已完成或全部通过。
5. **汇报绑定**：批次汇报的 check 结果旁必须引用校验记录位置；**没有记录不得说"已完成/全过"**。上下文压缩或切换批次后，先重读 02 与 01 当前段再动笔。
6. **评审与缺陷台账（放行门）**：GATE1.5 剧本、02、03 超过 6 镜的批次，以及每个正式 04 段和受影响的段间切点，按 `assets/templates-review.md` 独立评审。评审针对当前版本；01「质量缺陷台账」分别记机检、内容评审、发送前回读，不得以其中一项代替另一项。每项结论引用 `文件:行` 或节点证据；不适用须写明理由，未验证不得记 PASS。修复后排查同类问题并局部复审。
   - **剧本未过不冻结**：GATE1.5 未过时不推进受影响内容到正式分镜或提示词；正式 04 未过时不作为生成输入放行，发送状态按三节判定。没有独立评审条件时按二节记「待评审」，请求用户审当前稿并明确裁决；自评、笼统的「继续」和旧稿通过都不能替代。
   - **暂定路线与实图未到不阻塞工作稿**：在 GATE0 记录模型路线（`models.md`「项目路线记录」），阶段 2–4、5 分别按同一条路线编写 03、04。可交工作稿供审阅，但路线未确认、能力证据缺失或参考只在 PLAN 阶段时，不得标为可发送。换路线走一节的变更影响传播，不靠改模型标签掩盖两份稿的冲突。
   - **把适用知识带进产出**：写前按 `SKILL.md` 的读取时点找规则；批次留痕点名本批触发的规则及其落点（镜号或 `文件:行`）。与本批质量相关的规则若未采用，注明不适用的依据或待验证条件；只报「已读」不算落实。

**冻结字段禁止手打**：风格圣经、色板、角色/服装/道具锚定短语、台词原文——一律从 02/01/05 复制；手打 = 漂移源。发现文件与记忆不一致时，以文件为准并回读确认。

## 五、独立单镜试拍

- **触发条件**：用户明确只想独立试一个镜头，或只要一条单镜视频提示词，且不要求修改、续作既有项目或做正式交付。「一条提示词」若要包含多个镜头，仍走完整项目；既有项目的单镜修改仍走定向修改或局部重排。
- **先确认会影响这条提示词的信息**：复用用户给出的画幅、时长、参考素材和模型。只有缺失信息会改变镜头、又不能合理假设时才问一个问题；其余直接标明假设。模型未定时不承诺工具支持的时长或参考图能力；已指定模型时再查 `references/models.md`。
- **只交付两部分**：按 `references/prompt-rules.md` 的单镜提示词口径，给一条可复制的提示词（主体与起始画面、动作与结束画面、必要的机位/光线/声音）；再给一到两条回看要点，说明试拍成功时应该看到什么。不默认建项目文件，不调用生成 API，不把试拍稿标为已机检或已验收。
- **转入正式制作**：用户要扩成多镜、加入系列或正式交付时，按对应项目路由处理；新项目从 GATE0 开始，只补未确认的信息。试拍稿可复用为参考，不替代定稿、锚定确认或批次校验。这里的试拍不是校验器的「轻量 profile」。
